## 1. エグゼクティブサマリー

- **PHP 7.2 → 8.3.36** への変更に伴い、**ソースの一部改変は必須**です。フルパスを避けた `_assets/config.php`（`DOCUMENT_ROOT` 基準）などは移転に有利ですが、**かごや時代の絶対パス・DB ホスト・MT 設定・フォーム画像保存先**が残っています。
- **Movable Type 7**（URL **`/mt7/`**）は Perl CGI が本体。PHP 8 とは別に **`mt7` 配下の `mt-config.cgi`** のパス・DB・sendmail・ImageMagick をさくら（移転先）向けに合わせます。**旧 `/mt/` はかごやに温存のみで、今回さくら（移転先）へはコピーしません。**
- **MySQL はさくら（移転先）上**に移管します（§3-A）。
- **切替は DNS 一括**。切替時の短時間の不具合は許容します（§3-B）。
- **専用ステージングサーバーは設けません**。改修・配置は **さくら（移転先）上の本番相当環境**で進め、**§3-C の試験 URL**（初期ドメイン・試験運用ドメイン等）で DNS 切替前の確認を行います。
- 表サイトと **AWS 上の新バックオフィス**（`fmmie.backsite.pro`）の連携（formz / SSO 等）は、移転後も継続前提。**formin**（Kagoya バックアップ）は移転前に **§4.9 で一時停止**する方針を取れる（PHP 7.2 上の個人情報流入回避）。再開は移転・方針確定後に判断。

### 4.4 MT7 テンプレートの所在（正本 vs 旧コピー）

**MT7 で実際に使うテンプレの正本**は、表サイトリポジトリ次の **`_temps`** です（ローカルに無い分は **かごや mt7 上にのみ**存在）。

| ディレクトリ | 用途（MT ブログ想定） | ファイル数（目安） |
|--------------|------------------------|-------------------|
| `programs/_temps/` | 番組ブログ用 | 11（`_temp_*.php` / `.mtml` / CSS 等） |
| `profiles/_temps/` | 会社・プロフィール系 | 5 |
| `topics/_temps/` | トピックス・フォームキューブ等 | 5 |

**ローカル `_temps` の状態（2026-10-22 確認）**

- **`/home/kir691871` および `_app/` の記述は無い**。
- PHP インクルードは **`DOCUMENT_ROOT` + `_assets/config.php`** および **`INCLUDE_*_PATH` 定数**に統一済み。
- フォーム系（例: `profiles/_temps/_temp_message.php`, `topics/_temps/_temp_formcube.php`, `programs/_temps/_temp_message.php`）も **`_assets/apps/formz/*`** を参照。

**移転作業の意味**

- 旧 grep で出ていた **`mt/themes/...`（裏リポジトリ）** や **`service/_temlate/...`** は **旧 MT / 控え**に近く、**mt7 正本ではない**。
- かごや **mt7 内にだけ**残っているテンプレのうち、古い絶対パス・`_app` 参照がある場合は、**ファイル単位の置換より `_temps` 正本を MT7 に再反映**する方が安全（ドリフト解消兼ねる）。
- mt7 に **ローカル `_temps` に無いテンプレ**がある場合は、移転前に **MT 管理画面からエクスポート**し、パス有無を一覧化する。

### 4.5 レガシー `_app` と `_assets`（mt7 未同期時のみ）

- 表サイトアプリの正は **`_assets/apps/`**。
- **mt7 が `_temps` より古い**と、サーバー上テンプレだけ `_app` / かごや絶対パスを参照している可能性がある。
- **`_temps` と mt7 本番が一致していれば、テンプレ起因のパス改修はほぼ不要**（さくら（移転先）でも `DOCUMENT_ROOT` が `www` 直下になるだけ）。

#### 4.9 formin バックアップの一時停止（移転前・PHP 7.2 対応）

**背景（2026-10 時点）:** 世界的な PHP 脆弱性を契機に、**かごや PHP 7.2 上でリスナー投稿（個人情報）を Kagoya DB にバッファする運用**を移転完了まで避けたい、という関係者意向がある。formin（`24_formin-initial-spec.md`）は障害時の受信・閲覧・RDS 戻しが目的だが、仕様上 **通常時も** AWS ミラー（層 C）と表サイトリレーで Kagoya に投稿コピーが入る。**ソース改変は不要**で、本番設定 2 点の変更のみで **新規のバックアップ経路を一旦ストップ**できる。

| # | 場所 | 設定 | 効果 |
|---|------|------|------|
| **1** | **表・かごや** `fmmie.jp/_assets/apps/formz/formin_config.php`（**裏 `_tools/formin/config/` とは別ファイル**。Git 管理外・本番のみ） | `FORMIN_RELAY_ENABLED` → **`false`**（定数自体が無い場合は **既にリレー OFF** — `formin_regist.php` は未定義なら送信しない） | フォーム送信時の **経路 1**（`formin_regist` → `receive_submission.php`）を停止 |
| **2** | **AWS 本番** `fmmie.backsite.pro/backsite_fmmie/.env` | `FORMZ_MIRROR_ENABLED` → **`false`** | doc 23 **層 A/B/C** のミラー送信をすべて停止（**層 C＝投稿 push** 含む）。層 C だけ個別 OFF するフラグは現状なし |

**この 2 点で止まるもの**

- Kagoya `ad_formzdata` 等への **新規投稿コピー**（formin バックアップとしての流入）

**止まらない／影響しないもの**

- **formz（AWS）正本** — リスナー向けフォームの通常受信・管理・RDS は **従来どおり**
- **既に Kagoya DB に残っている行** — 設定 OFF だけでは削除されない（purge・手動削除は別判断）
- **`/_tools/formin/` 管理 UI** — MT メニュー・URL 直打ちは、別途触らない限り **閲覧可能なまま**（新規バッファは来ない）
- **層 A/B 停止の副作用** — AWS から Kagoya への **フォーム設定ファイル・マスタ DB ミラー**も止まる。障害時に Kagoya だけで formin を再稼働させる場合は、層 A のローカル `formzconfig` 鮮度に注意（再開方針で判断）

**本番反映時の注意**

- AWS: `.env` 変更後、`php artisan config:cache` 等を使っている場合は **キャッシュ再生成**
- ローカル Dropbox 上の `.env` / `formin_config.php` を編集しても **本番は変わらない** — かごや・AWS **本番ファイル**で実施

**再開（参考）**

- 上記を `true` に戻す（移転先 PHP 8.3・方針確定後）。§4.8.4 の cron・§9 試験を再実施。

**移転 WBS との位置づけ:** フェーズ 0〜1（かごや本番調査・改修着手）の **前または並行**で実施可。さくら移転後に formin を再開するかは **別途合意**（§9 の formin 試験項目は停止中はスキップ可）。

## 7. データベース移行（さくら（移転先） MySQL）

### 7.1 移行対象の整理

コード・設定から **最低限移す DB** は次の 2 つ（かごや上で `SHOW DATABASES;` し、名称が違えば読み替える）。

| DB 名（参考） | 利用者 | 内容の例 |
|---------------|--------|----------|
| **`fmmie_backsite`** | 表 `connectKami()`、裏 `admin_functions` / **formin** | フォーム定義・投稿データ（`ad_formz*` 等）、formin 用テーブル |
| **`mt7`** | MT7 **`mt-config.cgi`** | Movable Type 本体（記事・テンプレ・ユーザー・再構築設定） |

**移行対象外（別系統）**

- **`fmmie.backsite.pro`（AWS RDS / `backsite_fmmie`）** — Laravel 新バックオフィス。今回のかごや→さくら（移転先） MySQL 移行には含めない（formin は HTTP で連携継続）。

**要確認（使っていれば追加）**

- **`media_wp`** — 裏 `media_wp/wp-config.php` が参照。WordPress をさくら（移転先）でも使うなら **3 本目**として同手順でダンプ。

### 7.2 事前準備（さくら（移転先））

1. **サーバコントロールパネル** → **データベース** → MySQL データベースを **DB ごとに 1 つ作成**（例: `[account]_fmmiebs` / `[account]_mt7` — 実名はパネル表示に従う）。
2. **MySQL ユーザ**を作成し、上記 DB へ **すべての権限**を付与。
3. パネルに表示される **MySQL ホスト名**（例: `mysql[番号].db.sakura.ne.jp` または **`localhost`**）を控える。PHP / MT からは **パネル記載の値**を使う（同一サーバ内からは `localhost` が一般的）。
4. 文字コードは **utf8mb4**（照合順序は可能なら `utf8mb4_unicode_ci` 等。旧 DB が `utf8` のみならインポート後に問題が出たテーブルだけ見直し）。

### 7.3 ダンプ（かごや側）

**推奨:** かごや SSH 上で `mysqldump`（phpMyAdmin より再現性が高い。MT7 は容量が大きいことが多い）。

```bash
# 接続先はかごや MySQL（現行: o4043-462.kagoya.net 等。ユーザ/パスはサーバー設定）
KAGOYA_HOST='o4043-462.kagoya.net'
KAGOYA_USER='kir691871'
# パスワードは対話入力または ~/.my.cnf（平文をシェル履歴に残さない）

DATE=$(date +%Y%m%d)
OUT=~/db_export_${DATE}
mkdir -p "$OUT"

mysqldump -h "$KAGOYA_HOST" -u "$KAGOYA_USER" -p \
  --default-character-set=utf8mb4 \
  --single-transaction \
  --routines --triggers \
  --add-drop-table \
  fmmie_backsite | gzip -c > "$OUT/fmmie_backsite.sql.gz"

mysqldump -h "$KAGOYA_HOST" -u "$KAGOYA_USER" -p \
  --default-character-set=utf8mb4 \
  --single-transaction \
  --routines --triggers \
  --add-drop-table \
  mt7 | gzip -c > "$OUT/mt7.sql.gz"

# media_wp を使う場合のみ
# mysqldump ... media_wp | gzip -c > "$OUT/media_wp.sql.gz"
```

**初回（テスト用ドメイン試験）:** 上記ダンプを **そのまま**さくら（移転先）へ持ち込み、接続設定だけさくら（移転先）向けにした PHP/MT で動作確認（§3-C）。

**本番 DNS 切替直前:** 同コマンドで **再ダンプ**（切替窗口中の投稿・MT 更新を取り込む）。ダウンタイムを短くするなら、事前に全量インポート済みの DB に対し、切替時は **差分**ではなく **全量差し替え**（サイト規模上現実的）を §3-B の許容範囲で実施。

### 7.4 転送

```bash
# 例: ダンプをさくら（移転先）へ
scp "$OUT"/*.sql.gz [account]@[account].sakura.ne.jp:~/
```

（SSH ホスト名は契約サーバーに合わせる。）

### 7.5 インポート（さくら（移転先）側）

**A. SSH + mysql コマンド（推奨・大容量向け）**

```bash
cd ~
gunzip -c fmmie_backsite.sql.gz | mysql -h mysql[番号].db.sakura.ne.jp -u [account]_user -p [account]_fmmiebs
gunzip -c mt7.sql.gz           | mysql -h mysql[番号].db.sakura.ne.jp -u [account]_user -p [account]_mt7
```

**B. サーバコントロールパネルの phpMyAdmin（§3-F）**

- 対象 DB を選択 → **インポート** → `.sql.gz` が使えない場合は一度 gunzip した `.sql` を分割する、または A を使う。
- さくら（移転先）は **アップロードサイズ上限**があるため、MT7 が大きいときは A が安全。

### 7.6 アプリ設定の差し替え（インポート後必須）

本節は移転計画策定時点（**2026-10-30**）のレビュー結果。§11 リスクの補足として、**移転着手前・DNS 切替前**に確認すること。

### 13.1 さくら側の前提確認（最優先）

| 項目 | 内容 | 推奨アクション |
|------|------|----------------|
| **ドメインと実パス** | 本計画は **表＝`www` 直下・裏＝`www/backsite/`** の sibling 前提（§2.2） | サーバコントロールパネルで `fmmie.jp` / `backsite.fmmie.jp` の **ドキュメントルートが上記と一致するか**を契約直後に確定。別 `www`・サブディレクトリ不可等の制約があれば **§2.3・formin 相対パス・MT `includephppath` を再設計** |
| **PHP 8.3.36** | 文書上の移転先バージョン | パネルで **8.3 系（可能なら 8.3.36）** が選択できることを確認 |
| **SSH / rsync** | §6 — プランにより SSH が使えない | 使えない場合は **SFTP / ファイルマネージャ** での転送時間見積（mt7・`usr_img`・DB ダンプ） |
| **Perl CGI（MT7）** | PHP 8 とは別系統のボトルネックになりやすい | Perl パス、CGI 755、LF、**ImageMagick**、**SendMailPath**、再構築タイムアウトを試験 URL で確認（§9 に再構築・画像 UP を含める） |

### 13.2 ステージング無し × DNS 一括（§3-B/C）の実務

| 項目 | 懸念 | 推奨 |
|------|------|------|
| **切替窗口のデータ** | 最終 `mysqldump`（§7.3）以降の **フォーム投稿・MT 編集**はさくら DB に載らない | 許容範囲を関係者合意。可能なら窗口中は **フォーム POST・MT 編集を短時間停止** |
| **ロールバック** | DNS をかごやへ戻しても、切替後にさくらで書き込まれたデータは **かごや DB と整合しない** | 「DNS 戻し＝表示の復旧」までと割り切る、または **切替後 N 時間は書き込み最小** 等の運用ルールを事前文書化（フェーズ 7） |
| **試験 URL の限界** | `*.sakura.ne.jp` 等では **Cookie ドメイン・reCAPTCHA・SSO リダイレクト**が本番と一致しない | §9 の **formz SSO・formin・reCAPTCHA** は **本番ドメイン割当後に必須再テスト**（チェックリストに明記済み） |

### 13.3 ソース・本番の差分（grep 見落とし）

### 13.4 公開サイト・周辺で計画が薄くなりやすい点

| 項目 | 内容 |
|------|------|

### 13.5 連携・インフラ（事前作業が要るもの）

| 項目 | 懸念 | 推奨タイミング |
|------|------|----------------|
| **AWS formin ミラー / WAF** | 送信元 IP が **かごや → さくら** に変わる | **DNS 切替と同タイミング**（または直前）で許可リスト更新（§4.8.3） |
